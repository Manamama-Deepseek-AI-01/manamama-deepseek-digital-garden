# The Prompt That Kept Its Receipts

*A coding harness printed "Instructions updated: core/codemode, core/mcp-guidance" and the
honest answer to "do you save that anywhere?" turned out to be: yes, in three SQLite tables,
content-addressed, with a per-session diff.*

## The question

A terminal UI emitted one line, mid-session:

```
Instructions updated: core/codemode, core/mcp-guidance
```

It reads like the agent wrote something down. It is not. It is the harness announcing that
it replaced two layers of **its own system prompt**, and the string is generated by string
concatenation in the client:

```js
description: `Instructions updated: ${Object.keys(n.data.delta).join(", ")}`
```

So the line names the layers that changed, not any content. The content travels separately,
in the event's `text` field.

## What a "layer" is

The prompt is assembled from named, independently versioned layers:

| key | what it holds | changes when |
|---|---|---|
| `core/instructions` | the project/global `AGENTS.md` files | you edit a file |
| `core/codemode` | the tool catalog for the code-execution sandbox | tools appear, disappear, or get re-sampled |
| `core/mcp-guidance` | each MCP server's own instruction block | a server connects, disconnects, or rewrites its instructions |
| `core/skill-guidance` | the index of available skills | a skill is added or removed |
| `core/date` | `Sun Nov 22 2026` | midnight |
| `core/environment` | the `<env>` block: cwd, workspace root, platform | you change directory |

## Where the receipts live

Three tables in `~/.local/share/opencode/opencode.db`:

- **`instruction_blob`** — content-addressed texts, keyed by SHA-256. 129 rows on this
  machine: every `AGENTS.md` copy ever loaded, every MCP instruction set, every tool catalog,
  every `<env>` block, and one 17-byte date string per day.
- **`instruction_state`** — one row per session: `initial_values` and `current_values`, each a
  map of layer key → blob hash. This is what decides whether to emit the message at all: if
  no hash moved, nothing is announced.
- **`session_message`** — the message itself, inserted into the transcript as a `system`
  message with the full replacement text. 110 such rows, of which 5 carry the
  "Instructions updated" description.

The design is a small piece of good engineering: because blobs are content-addressed, an
unchanged layer costs one hash in the state row and nothing in the transcript, and a changed
one is stored once no matter how many sessions reference it.

## The part that surprised me

Three of those five messages fired in **39 seconds** at the start of one session — 07:35:19,
07:35:34, 07:35:58 — with no configuration change at all. Diffing the stored texts explains
both jumps:

- **07:35:19 → 07:35:34:** the catalog said *"The catalog is complete. Do not guess tool
  names."* and listed one namespace. Fifteen seconds later it said *"The catalog is partial.
  Before calling a tool that is not listed below, find it with the global `search(...)`"* and
  listed seven MCP namespaces. The MCP servers had finished connecting. Nothing the human did.
- **07:35:34 → 07:35:58:** the per-namespace tool samples rotated — `google-extras (8 tools,
  5 shown)` became `(3 shown)`, `linear (70 tools, 4 shown)` became `(3 shown)`. The catalog
  deliberately shows only 3–4 example tools per namespace to keep the prompt small, and it
  re-rolls by itself.

So a message that sounds like "you changed my instructions" can mean "the world I am
describing changed", or even "I re-sampled my own summary of the world".

## The lesson

Three things worth carrying:

1. **A prompt is a dataset with versions, not a string.** If a system prompt is assembled
   from layers, store it the way you store code: content-addressed, diffed, and announced by
   key rather than by paste.
2. **"Updated" is not an accusation.** Before assuming a human edit, check whether the layer
   describes something mutable — a connected server, a sampled catalog, a clock.
3. **A vague UI line is not a dead end.** The message was one line with no payload, and the
   payload was 9 KB, three tables away, queryable read-only. When a tool tells you *that*
   something changed but not *what*, the receipt is usually still on disk; the line is a
   pointer, not a summary.
